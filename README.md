## Алгоритм работы

1. `script.sh` запущен.
2. В другом терминале проверен файл `my.log` - в него добавляются новые записи.
3. Удален файл скрипта и затем проверенно что `my.log` пополняется новыми записями. Команды отображенны в файле `afterDeletion.log`
4. Поиск процесса и его дескриптора для получение удаленного скрипта. команды в файле `findDeletedScript.log`
5. Сохранение удаленного скрипта в файл `restoredscript.sh`

## Почему процесс продолжает работать после удаления файла

В Linux файл — это inode; имя в каталоге — лишь одна из ссылок на него.
`rm` выполняет системный вызов `unlink()` для файла `/opt/script.sh`. При этом удаляется его вхождение в каталог `/opt` ("линк"). Поэтому получить содержимое файла через имя в каталоге больше не получится.
А inode и данные остаются, пока на них есть хотя бы одна ссылка. Открытый файловый дескриптор процесса — тоже ссылка на inode. `bash /opt/script.sh` держит FD (обычно 255) на скрипт всё время работы, поэтому после `rm` процесс продолжает выполняться и писать в `/opt/my.log`.

## Механизм получения содержимого удалённого файла

Механизм — виртуальная файловая система procfs, каталог `/proc/<PID>/fd/`. Ядро в этом файле показывает открытые дескрипторы процесса как симлинки; для удалённых файлов путь помечается `(deleted)`. Чтение `/proc/<PID>/fd/<FD>` возвращает содержимое inode, а не открывает файл по имени — это и позволяет восстановить удалённый скрипт.
